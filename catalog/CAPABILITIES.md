## Project creation

Two ways to start a new Altruist server: the `altruist` dotnet template and the `altruist create` command of the Altruist.CLI tool. Both give you the same ready-to-run project with Program.cs, config.yml, one WebSocket portal and one REST controller.

**Use it when**

- When you start a new Altruist server from nothing and want a project that runs at once.
- When you want a known-good layout (Program.cs, config.yml, Portals/, Http/) to copy from.
- When you want a short command to run the current project (`altruist run`, which calls `dotnet run`).

**Don't use it when**

- When you add Altruist to an existing .NET project, add the packages by hand and write config.yml yourself; see application.
- When you need a game with rooms, combat or inventory, create the project first, then add those packages (see the gaming capabilities).

**Packages:** `Altruist.CLI`, `Altruist.Templates` · **Docs:** [/docs/getting-started/installation](https://altruist-docs.vercel.app/docs/getting-started/installation), [/docs/getting-started/quick-start-guide](https://altruist-docs.vercel.app/docs/getting-started/quick-start-guide)

```bash
# Option 1: the dotnet template (installs once, then works offline)
dotnet new install Altruist.Templates
dotnet new altruist -n MyServer
cd MyServer
dotnet run

# Option 2: the CLI tool (installs the template for you if it is missing)
dotnet tool install -g Altruist.CLI
altruist create MyServer
cd MyServer
altruist run          # same as: dotnet run
```

The project name must start with a letter and may contain letters, digits, `_` and `.`.
The template creates `Program.cs` (`await AltruistApplication.Run(args);`), `config.yml`
(HTTP on 0.0.0.0:8080, a JSON WebSocket at `/ws`, an in-memory cache), `Portals/HelloPortal.cs`
and `Http/HelloController.cs`. It references the packages Altruist, Altruist.Boot, Altruist.Socket and Altruist.Web.

## Configuration

Altruist is configured from YAML, not from builder code. `config.yml`, then `config.{environment}.yml`, then environment variables, then command-line arguments are merged (later wins), and attributes pull the values into your classes. The same attributes can also switch whole services on or off.

**Use it when**

- When a value (port, rate, key, provider) should come from config.yml instead of being hard-coded; use `[AppConfigValue]` on a constructor parameter.
- When a group of related settings belongs in one typed object; use `[ConfigurationProperties]`.
- When a value must change while the server runs (tunables); use `ILiveConfigValue<T>`.
- When a service should exist only if a config key is set, a package is installed, or no other implementation is registered; use `[ConditionalOnConfig]`, `[ConditionalOnAssembly]` or `[ConditionalOnMissingService]`.
- When you need one instance per entry of a YAML list (for example one per world); use a list-mode `[ConditionalOnConfig(path, KeyField = "id")]` with `*:` paths.

**Don't use it when**

- When you only need to register a service without any settings, use `[Service]`; see services-and-modules.
- When a value is a secret, keep it out of the committed YAML and set it by environment variable or `${NAME}` placeholder.
- When you need the settings of one specific system (email, security, rooms), read that capability's config keys instead of the general mechanics here.

**Packages:** `Altruist`, `Altruist.DI` · **Docs:** [/docs/getting-started/configuration](https://altruist-docs.vercel.app/docs/getting-started/configuration)

How the sources combine (later wins):

1. `config.yml` and `config.{environment}.yml` in the build output folder. The environment is `DOTNET_ENVIRONMENT`,
   else `ASPNETCORE_ENVIRONMENT`, else `Production` (`AltruistEnvironment.Name`), so `config.Development.yml` loads in Development.
2. Environment variables: the key path upper-cased, `__` for `:` and `_` for `-`.
   `ALTRUIST__SERVER__HTTP__PORT=9090` sets `altruist:server:http:port`. Your own YAML roots work too (`MYAPP__MAIL__API_KEY`).
3. Command line: `--altruist:server:http:port=9090`.

A YAML value may read an environment variable: `${NAME}` or `${NAME:-default}`.

```yaml
# config.yml: keys are kebab-case under `altruist:`, your own settings live under your own root
altruist:
  environment:
    mode: 2D                  # 2D or 3D; the game systems read it
  server:
    http:
      host: 0.0.0.0
      port: ${PORT:-8080}
  game:
    worlds:
      items:                  # a list: one World per item, keyed by id
        - id: overworld
          size: { x: 1000, y: 1000 }
          gravity: { x: 0, y: 0 }

myapp:
  mail:
    host: smtp.example.com
    port: 587
  match:
    tick-rate: 60
```

## Services, dependency injection and modules

Altruist finds your classes by attribute and wires them into the DI container, so you never write a Startup class. `[Service]` registers a class, `[ServiceConfiguration]` runs a step that adds registrations by hand, `[Bean]` registers a factory method, and `[AltruistModule]` runs one-time startup code once everything is built.

**Use it when**

- When you need an object you build by hand (a type you cannot annotate); use a `[Bean]` method.
- When one-time startup work needs several services together (seeding a registry); use an `[AltruistModule]` static class with an `[AltruistModuleLoader]` method.
- When a service needs initialization after the container is built, use a `[PostConstruct]` method.

**Don't use it when**

- When the setting is only a value or a section of YAML, use `[AppConfigValue]` or `[ConfigurationProperties]`; see configuration.
- When you need a service locator in normal code, inject through the constructor. `Dependencies.Inject<T>()` is for static helpers only.
- When your process needs no server (a worker or tool), use `AltruistDI.Run(args)` and not the full application; see application.

**Packages:** `Altruist.DI`, `Altruist` · **Docs:** [/docs/altruist/di](https://altruist-docs.vercel.app/docs/altruist/di), [/docs/extension/service](https://altruist-docs.vercel.app/docs/extension/service)

```csharp
// A service, injectable as IScoreService
[Service(typeof(IScoreService))]
public sealed class ScoreService : IScoreService
{
    public ScoreService(ILogger<ScoreService> log, [AppConfigValue("myapp:score:max", "100")] int max) { /* ... */ }

    [PostConstruct]                                   // runs once after the container is built
    public Task InitAsync(IRepository repo) => repo.PreloadAsync();
}

// A step that adds registrations by hand; lower order runs first
[ServiceConfiguration(order: 10)]
public sealed class MailSetup : IAltruistConfiguration
{
    private readonly string _host;
    public MailSetup([AppConfigValue("myapp:mail:host", "localhost")] string host) => _host = host;
    public bool IsConfigured { get; set; }
    public Task Configure(IServiceCollection services)
    {
        services.AddSingleton(new SmtpClient(_host));
        return Task.CompletedTask;
    }
}

// One-time startup wiring after every service exists, before HTTP starts
[AltruistModule("Shop")]
public static class ShopModule
{
    [AltruistModuleLoader]
    public static async Task Load(ICatalog catalog) => await catalog.SeedAsync();
}
```

## Application bootstrap and lifetime

`AltruistApplication.Run(args)` is the whole entry point of a server. It loads configuration, registers everything found by attribute, builds the container, runs modules, starts HTTP and the transports, and tracks readiness. Built-in health endpoints report the result.

**Use it when**

- When another part of the app needs to know whether the server is ready (database and cache connected); inject `IServerStatus`.
- When a load balancer or Kubernetes probe needs a health check; use `GET /altruist/health` and check the `Online` field.
- When a service connects to something external and should delay readiness until it is up; implement `IConnectable`.

**Don't use it when**

- When you need only the DI container, with no HTTP and no transports, use `AltruistDI.Run`; see services-and-modules.
- When you want to change what the app does, do not edit bootstrap; add services, modules or config instead.

**Packages:** `Altruist`, `Altruist.Boot` · **Docs:** [/docs/getting-started/introduction](https://altruist-docs.vercel.app/docs/getting-started/introduction)

```csharp
// Program.cs
using Altruist;

await AltruistApplication.Run(args);   // blocks until shutdown; args are the highest-priority config source
```

```csharp
// Wait for readiness, and read what the server is
[Service]
public sealed class Announcer
{
    private readonly IServerStatus _status;
    private readonly IAltruistContext _context;
    public Announcer(IServerStatus status, IAltruistContext context) { _status = status; _context = context; }

    public bool CanServe => _status.Status == ReadyState.Alive;    // Starting, Alive or Failed
    public string Address => $"{_context.ServerInfo.Protocol}://{_context.ServerInfo.Host}:{_context.ServerInfo.Port}";
}
```

<a id="server-engine"></a>

## Server engine and scheduling

The engine is the fixed-rate loop of the server: it runs recurring tasks, timers and effects every frame and applies state changes on one thread. Here live its contract (`IEngineCore`, `IAltruistEngine`), cron presets and the engine-aware router; the loop itself ships in Altruist.Gaming. It is not a web server and not a physics engine.

**Use it when**

- When game state is changed from a network or request thread and must be applied on the engine thread; use `WaitForNextTick` or `SyncCommit`.
- When you need a one-shot timer (`ScheduleOnce`), a buff that repeats until it expires (`ScheduleEffect`) or slow I/O whose result the game needs (`RunOffTick`).
- When work must run on the wall clock (daily reset, pruning); use `RegisterCronJob` with a `CronPresets` expression (UTC).
- When you serialize work per entity; use `SendTask` with a stable `TaskIdentifier`.

**Don't use it when**

- When the code is plain request handling with no game loop, do not turn the engine on; leave `altruist:game:engine` out of config.
- When you want a recurring method, mark it with the `[Cycle]` attribute; see the gaming capabilities.
- When you want the game tick, world step and physics, see the Gaming Main capabilities; this capability only describes the shared contract.

**Packages:** `Altruist`, `Altruist.Gaming` · **Docs:** [/docs/altruist/engine](https://altruist-docs.vercel.app/docs/altruist/engine)

```yaml
# Presence of this section turns the engine on
altruist:
  game:
    engine:
      framerateHz: 30      # frames per second; default 30
      diagnostics: false   # true logs how long each task takes
```

```csharp
[Service]
public sealed class Respawner
{

    public Respawner(IAltruistEngine engine) => _engine = engine;

    // from a network handler: change state on the engine thread
    public void Move(Player p, Vector2 to) => _engine.WaitForNextTick(() => p.Position = to);

    // a one-shot timer
    public void ScheduleRespawn(string playerId) =>
        _engine.ScheduleOnce(TimeSpan.FromSeconds(3), () => Respawn(playerId));

    // wall-clock job (UTC), runs on the thread pool, not the engine thread
    public void ResetDaily() => _engine.RegisterCronJob(DailyReset, CronPresets.Daily);

    private static Task DailyReset() => Task.CompletedTask;
    private void Respawn(string id) { /* ... */ }
}
```

## Email

**Use it when**

## Core utilities

Small helpers used across the framework and open to your code: a thread-safe pool for scratch collections, route and reflection helpers, and flag-enum helpers that do not mutate.

## Transports and connections

The listeners that accept client connections: TCP, UDP and WebSocket, plus the connection manager that tracks every live connection. You turn each transport on in config.yml and any mix can run at once. Portal code stays the same on all of them.

**Use it when**

- When you need a browser client (WebSocket), a reliable desktop or mobile stream (TCP) or fast unreliable updates (UDP).
- When you need to cap connections, set the idle timeout or change a port.
- When you write a new kind of transport (implement ITransport) or need to look up or close a connection by id.

**Don't use it when**

- When you need to handle what clients send, use portals-and-routing instead. Transports only deliver bytes.
- When you need to choose the message format (JSON or MessagePack), use packets-and-codecs instead.
- When you need REST endpoints, use http-api instead.

## Portals, gates and routing

A portal is a class that handles client messages. Each gate method on it handles one event name, and the router sends replies to one client, a room or everyone. Interceptors can inspect or drop packets before a gate runs, and an outbound queue can send without blocking your handler.

**Use it when**

- When you send a packet to one client, a room or all clients with IAltruistRouter.
- When you need to react to a client connecting or disconnecting (OnConnectedAsync, OnDisconnectedAsync).
- When you filter or log every incoming packet with an IInterceptor, or send through the queued outbound mode for busy game loops.

**Don't use it when**

- When you need to limit how fast a client may send, use rate-limit instead. It is built on interceptors.
- When you only need to send entity changes (changed properties), use entity-sync instead.
- When you serve plain request and response over HTTP, use http-api instead.

**Packages:** `Altruist` · **Docs:** [/docs/networking/portals](https://altruist-docs.vercel.app/docs/networking/portals), [/docs/networking/router](https://altruist-docs.vercel.app/docs/networking/router)

```csharp
using Altruist;

[Portal("/game")]
public class ChatPortal : Portal
{
    private readonly IAltruistRouter _router;

    public ChatPortal(IAltruistRouter router) => _router = router;

    [Gate("chat")]
    public Task OnChat(ChatPacket packet, string clientId)
        => _router.Broadcast.SendAsync(packet, excludeClientId: clientId);

    [Gate("whisper")]
    public Task OnWhisper(WhisperPacket packet, string clientId)
        => _router.Client.SendAsync(packet.TargetId, packet);
}
```

**Attributes**

- `[Coalesce]`: Marks a packet type whose queued copies supersede each other: a client's outbound queue keeps at most one unsent packet per key (the newest, moved behind everything queued before it), so a client that reads slowly skips stale states instead of building a backlog.

## Packets and codecs

Packets are the typed messages sent between client and server, each with a numeric message code. Codecs turn them into bytes: JSON for browsers and debugging, MessagePack for compact binary. The Altruist.Protocol package holds the shared packet contracts, so other projects can use them without the server.

**Use it when**

- When you choose JSON or MessagePack for all transports or per transport.
- When you need the built-in packets (handshake, text, success or failed results, sync) or the transport result codes.
- When you add a new wire format by implementing ICodec and registering it with [CodecProvider].

**Don't use it when**

- When you handle a packet on the server, use portals-and-routing instead.
- When you send many numeric rows every tick in a compact positional form, use snapshots instead.

## Rate limiting for portals

A per-connection token-bucket limiter that runs before every gate handler. It drops packets that come too fast or are too large, and closes the connection of a client that keeps breaking the limits. It is installed from config.yml, with no code.

**Use it when**

- When clients can spam gates (chat, input, matchmaking) and you want hard limits per gate.
- When you cap the payload size of incoming packets.
- When you assign a gate to a bucket in code with [RateLimit("bucket")].

**Don't use it when**

- When you limit HTTP endpoints, use http-api instead. It has its own named policies (the same [RateLimit] attribute works there).
- When you need custom per-packet logic that is not a rate, write an IInterceptor (see portals-and-routing).

## Entity synchronization

Delta sync for world entities. Mark properties with [Synced] and the class with [Synchronized], and Altruist sends clients only the properties that changed, as a SyncPacket.

**Use it when**

- When world objects (players, NPCs) change a few properties per tick and clients should get only the changes.
- When you send an entity's changes by hand with IAltruistRouter.Synchronize.

**Don't use it when**

- When you send positional numeric rows for many objects every tick, use snapshots instead.
- When you send rare, mixed messages, use a normal packet (packets-and-codecs) instead.

**Packages:** `Altruist` · **Docs:** [/docs/networking/synchronization](https://altruist-docs.vercel.app/docs/networking/synchronization)

```csharp
using Altruist;

{
    public string ClientId { get; set; } = "";   // must not be empty for auto sync

    [Synced(0)] public uint VirtualId { get; set; }
    [Synced(1, SyncAlways: true)] public string Name { get; set; } = "";
    [Synced(2)] public int Health { get; set; } = 100;

    public PlayerEntity(Transform3D transform) : base(transform) { }

```

**Key types**

- `Altruist.ClientSynchronizator`: Placeholder `IClientSynchronizator` registered when only the transport is configured.

**Services**

- `[Synced]`: Marks a public instance property of an `ISynchronizedEntity` as part of its network-synchronized surface.
- `[Synchronized]`: Marks an ISynchronizedEntity class for automatic delta synchronization.

<a id="snapshots"></a>

## Snapshot schemas

A way to declare once in C# how a fast-changing state row (a float array with no field names) is laid out. The same declaration builds the server's allocation-free encoder and exports a JSON schema for the clients' decoders.

**Use it when**

- When you send numeric state of many objects every tick (players, projectiles, match clock) as compact MessagePack rows.
- When the server and several clients must agree on what each position of a row means.

**Don't use it when**

- When only changed properties should travel, use entity-sync instead.
- When messages are rare or hold names, lists and nested objects, use a plain packet (packets-and-codecs) instead.

**Packages:** `Altruist` · **Docs:** [/docs/networking/snapshot-schema](https://altruist-docs.vercel.app/docs/networking/snapshot-schema)

```csharp
using Altruist.Networking;

public static class Wire
{
    // Build once: the encoder compiles into one writer delegate
    public static readonly SnapshotRowSchema<Ship> ShipRow = SnapshotRowSchema.For<Ship>("ship")
        .Int("id", s => s.Id)
        .Number("x", s => s.Body.Position.X)
        .Number("y", s => s.Body.Position.Y)
        .Bool("shielded", s => s.Shielded)
        .Build();
}

float[] row = Wire.ShipRow.Encode(ship);          // exactly one row
Wire.ShipRow.Encode(ship, buffer, offset);        // no allocation
```

**Key types**

- `Altruist.Networking.SnapshotRowSchema`: Entry points for `SnapshotRowSchema`: `For` declares a row in code (computed values, several views of one type, state classes you do not want to annotate); `FromAttributes` builds one from `SnapshotFieldAttribute`s on the state class itself (plain fields / properties, the declaration sits next to the data).
- `Altruist.Networking.SnapshotRowSchema<T>`: A declarative, positional snapshot row: the ordered list of values a server writes for one object of type T (a player, a ball, the match clock...) as a `float[]`, which MessagePack sends as a compact array (no names on the wire).
- `Altruist.Networking.SnapshotSchemaSet`: The snapshot rows and packets a server sends, exported as one JSON document (format `Format`) that client decoders read (`@altruist/net`: `SnapshotSchema`).
- `Altruist.Networking.ISnapshotRowSchema`: Non-generic view of a `SnapshotRowSchema` (export, validation, tooling).
- `Altruist.Networking.SnapshotField`: One slot of a `SnapshotRowSchema`: its wire name, position and kind.

**Attributes**

- `[SnapshotField]`: Marks a public field or property as one slot of a positional snapshot row built with `FromAttributes`.
- `[WireField]`: Describes one member of a MessagePack packet (a `[Key(n)]` property) for the snapshot schema export: what the member holds and what a decoder uses when an older writer's packet array ends before it.

<a id="accounts-and-auth"></a>

## Accounts and Authentication

Everything for signing players in: BCrypt password hashing, HS256 JWT access tokens, rotating refresh tokens in an HttpOnly cookie, one-time tokens (email verification, password reset), session tokens for sockets, and the [Shield] attributes that protect portals and controllers on every transport. Altruist keeps the security-sensitive parts and leaves your account model to you.

**Use it when**

- When players must log in and you want signed access tokens, refresh tokens that detect stolen sessions, and password hashing that is already done right.
- When a portal (WebSocket, TCP or UDP) or an HTTP controller must only be reachable by authenticated clients ([JwtShield], [SessionShield], [Shield(typeof(...))]).
- When you need email verification or password reset links (one-time tokens) or a custom IShieldAuth such as an API key check.
- When you want a ready login controller to extend (JwtAuthController gives signup, login, refresh and upgrade endpoints).

**Don't use it when**

- When a browser must open a WebSocket and cannot set an Authorization header, use connection-tickets instead of putting the token in the URL.
- When you need to slow down password guessing or sign-up bots, add abuse-protection (lockout and captcha) on top.
- When you only need request throttling, use the HTTP and socket rate limits of the networking capabilities, not auth.

**Packages:** `Altruist` · **Docs:** [/docs/altruist/auth](https://altruist-docs.vercel.app/docs/altruist/auth), [/docs/altruist/auth/accounts](https://altruist-docs.vercel.app/docs/altruist/auth/accounts), [/docs/altruist/auth/fast-auth](https://altruist-docs.vercel.app/docs/altruist/auth/fast-auth), [/docs/extension/security](https://altruist-docs.vercel.app/docs/extension/security)

Safe by default: tokens are HS256 only and need an expiry; passwords use BCrypt (work factor 11); the refresh
token lives in an HttpOnly cookie and only its SHA-256 is stored. Not safe by default: if `key` is unset Altruist
uses a PUBLIC development key. In Production an app with an `altruist:security` section refuses to start when the
key is unset, is the development key, or is shorter than `min-key-bytes` (32 bytes). Set the key from the
environment, for example `ALTRUIST__SECURITY__KEY=$(openssl rand -base64 48)`.
Pick `password:prehash` before you store hashes: hashes of the two modes do not verify against each other.
```yaml
altruist:
  security:
    mode: jwt                  # jwt (default) | session
    key: ""                    # set from ALTRUIST__SECURITY__KEY, never commit it
    min-key-bytes: 32          # shorter keys are refused in Production
    access-token-minutes: 15
    password:
      work-factor: 11          # BCrypt cost, 4-31
      prehash: none            # none | sha384 (sha384 stops the 72-byte BCrypt truncation)
    refresh-tokens:
      lifetime-days: 30
      max-sessions: 10
    refresh-cookie:
      same-site: strict        # strict | lax | none
```

## Lockout and Captcha

Two small building blocks against password guessing and sign-up bots. IFailureLockout locks a key after repeated failures; ICaptchaVerifier checks a Turnstile, hCaptcha or reCAPTCHA token on the server. Both are registered by default and do nothing until you call them.

**Use it when**

- When a login or reset endpoint needs a lockout after N failures inside a time window.
- When the failure budget must hold across a fleet of servers (set lockout store to backplane, which needs Redis).
- When sign-up or login needs a captcha check on the server.

**Don't use it when**

- When you only want to cap request volume per client, use the HTTP or socket rate limits instead.
- When you need to prove who a player is, use accounts-and-auth. Lockout and captcha do not authenticate.

**Packages:** `Altruist`, `Altruist.Redis` · **Docs:** [/docs/altruist/auth/abuse](https://altruist-docs.vercel.app/docs/altruist/auth/abuse), [/docs/extension/shield](https://altruist-docs.vercel.app/docs/extension/shield)

```yaml
      secret-key: ""           # from ALTRUIST__SECURITY__CAPTCHA__SECRET_KEY
```

## Connection Tickets

One-time tickets that let a browser open an authenticated WebSocket without putting a long-lived token in the URL. The client trades its access token for a ticket valid for seconds, connects with ?ticket=, and the portal's [TicketShield] redeems it exactly once.

**Use it when**

- When a browser client connects to a portal over WebSocket and cannot send an Authorization header.
- When tickets issued by one server must be redeemed by another (they live in the fleet backplane, so use Redis for a fleet).

**Don't use it when**

- When the client can send a header (native, TCP or UDP clients), use [JwtShield] or [SessionShield] from accounts-and-auth.
- When you need a long-lived login token or a refresh flow, use accounts-and-auth. A ticket is single-use and short.

**Packages:** `Altruist`, `Altruist.Redis` · **Docs:** [/docs/altruist/auth/tickets](https://altruist-docs.vercel.app/docs/altruist/auth/tickets)

Safe by default: only the SHA-256 of a ticket is stored, redemption is an atomic take (a second use fails), and
request log lines that contain the ticket URL are reduced to warnings (`redact-request-logs: true`). Write the
issuing endpoint yourself so your own rules (bans, maintenance) apply.
```yaml
altruist:
  security:
    tickets:
      query-param: ticket
      ttl-seconds: 30
      max-per-principal: 4
      session-hours: 12
      redact-request-logs: true
```

## Persistence and the Unified Object Model

The data layer: model classes marked with [Vault] attributes (the Unified Object Model, UORM) map to database tables, a database provider connects to the database, and [Transactional] wraps service methods in a transaction. You write the model once and the provider creates and migrates the table.

**Use it when**

- When you need to store players, items or any game data in a database and describe the tables as C# classes.
- When several operations must succeed or roll back together ([Transactional] on a service method).
- When you want to route a model to a read replica or another database instance (DbInstance on [Vault]).
- When you want to seed data at startup (IDatabaseInitializer).

**Don't use it when**

- When you only need fast shared in-memory or Redis state with no tables, use cache instead.
- When you flush many hot, frequently changing rows, use autosave on top of the vault.
- When you need to read or write rows, use vault (IVault of T). This capability is the model and provider layer.

## Vault (IVault)

IVault of T is the API your code uses to read and write one table: fluent Where, OrderBy, Skip and Take, then async terminals such as ToListAsync, FirstOrDefaultAsync, SaveAsync, UpdateAsync and DeleteAsync. It also keeps a history table when the model asks for it.

**Use it when**

- When you query, save, update or delete rows of a [Vault] model.
- When you need an audit trail of saves (StoreHistory on [Vault], then SaveAsync with saveHistory true).
- When you need joins over several vault tables (IVaultJoinQuery).

**Don't use it when**

- When you load a root record with its related rows in one call, use prefabs.
- When a hot object is changed many times a second, use autosave so the database is hit in batches.
- When the data is not relational, use cache.

**Packages:** `Altruist`, `Altruist.Postgres` · **Docs:** [/docs/altruist/persistence/vault](https://altruist-docs.vercel.app/docs/altruist/persistence/vault), [/docs/altruist/persistence](https://altruist-docs.vercel.app/docs/altruist/persistence)

```csharp
[Service]
public class PlayerService(IVault<PlayerVault> players)
{
    public Task<List<PlayerVault>> TopAsync() =>
        players.Where(p => p.Level >= 50).OrderByDescending(p => p.Level).Take(20).ToListAsync();

    public Task SaveAsync(PlayerVault player) => players.SaveAsync(player, saveHistory: true);

    public Task LevelUpAsync(string id) => players
        .Where(p => p.StorageId == id)
        .UpdateAsync(s => s.SetProperty(p => p.Level, p => p.Level + 1));

    public async Task<bool> ExistsAsync(string name) => await players.AnyAsync(p => p.Name == name);
}
```

## Cache

A key-value cache behind one interface, ICacheProvider, with an in-memory backend (default) and a Redis backend. It holds hot or shared state such as session tokens and cross-server data.

**Use it when**

- When several servers must see the same state (use the Redis provider).
- When tests or a single dev server should run without Redis (use the inmemory provider).

**Don't use it when**

- When data must survive a restart, store it with vault. The in-memory cache loses everything on restart.
- When you need queries and relations, use vault.

## Prefabs

A prefab is a composite entity that loads and saves a root vault model together with its related rows (single references and collections) in one call. It saves only the parts that changed, in one batched statement.

**Use it when**

- When a player or character is spread over several tables (account, items, equipment, guild) and you load it as one object.
- When you filter by the root or by a child (Any on a collection) and eager-load only the components you need.

**Don't use it when**

- When one table is enough, inject IVault of T directly.
- When a save must also delete removed children. Prefab saves are upserts only; delete through the child's vault.

**Packages:** `Altruist`, `Altruist.Postgres` · **Docs:** [/docs/altruist/persistence/prefabs](https://altruist-docs.vercel.app/docs/altruist/persistence/prefabs)

<a id="migrations"></a>

## Code-First Migrations

At every start Altruist compares your [Vault] models with the live database schema and applies the difference: new tables, columns, indexes, unique keys and foreign keys, a primary key an existing table lacks, renames and type changes. There are no migration files and no CLI. Destructive changes happen only when you ask for them.

**Use it when**

- When you add, rename or retype a column and want the database to follow the C# model on restart.
- When you move data between columns ([VaultColumnCopy], [VaultRenamedFrom]) or retire tables ([VaultTableDelete], [VaultArchived]).

**Don't use it when**

## Redis Module

The Redis connection and its building blocks: the shared connection factory, Redis-backed message routers and ingress/egress endpoints for multi-server pub/sub. ## Autosave

Batched, cache-first saving for vault models. You mark an object dirty and Altruist flushes dirty objects to the database on an interval, in batches, with a write-ahead log for crash recovery. It cuts thousands of single writes into a few batched ones.

**Use it when**

- When many players or entities change often (position, gold, stats) and writing each change would overload the database.
- When a crash should lose at most a few seconds of changes (the write-ahead log is on by default).

**Don't use it when**

- When a change must be in the database before you continue (a trade, a purchase), call SaveAsync on the autosave service (cache and database now) or use a vault transaction.
- When you only create new rows or run queries, use vault directly.

**Packages:** `Altruist.Gaming.Autosave` · **Docs:** [/docs/altruist/persistence/autosave](https://altruist-docs.vercel.app/docs/altruist/persistence/autosave)

The interval and batch size come from the attribute first, then from config, then from the built-in defaults
(every 5 minutes, batch 100). `Wal = false` turns the write-ahead log off for low-value, high-frequency data.
```yaml
altruist:
  game:
    autosave:
      default-interval: "*/1 * * * *"
      default-batch-size: 200
      wal:
        enabled: true
        directory: data/wal
        flush-interval-seconds: 1
```
```csharp
[Autosave(120, AutosaveCycle.Seconds, BatchSize = 200)]
[Vault("players")]
public class PlayerVault : VaultModel { /* columns */ }

[Service]
public class CharacterService(IAutosaveService<PlayerVault> autosave)
{
    public Task<PlayerVault?> JoinAsync(string id) => autosave.LoadAsync(id);   // cache first
    public void Move(PlayerVault p, int x) { p.X = x; autosave.MarkDirty(p); }    // no database hit now
    public Task TradeAsync(PlayerVault p) => autosave.SaveAsync(p);               // cache and database now
}
```

<a id="fleet-and-server-nodes"></a>

## Fleet, Capacity and Drain

Runs one game on many servers. Every server is a node with a capacity budget, a drain (stop taking new work, let running work finish, then exit), health endpoints, and a heartbeat into a shared backplane. A fleet registry, a relay (?node=) and shared counters let a client reach the right server and let limits hold across servers.

**Use it when**

- When you run more than one copy of the server (Docker, Kubernetes) and rooms, lobbies or queues must find each other.
- When you need a load budget (max-load), readiness and liveness probes, or a graceful scale-down on SIGTERM.
- When tickets, rate limits or lockouts must be counted once for the whole fleet (shared counters in the backplane).

**Don't use it when**

- When you only need independent shards that never talk to each other, use multi-channel servers.
- When you want to store game data, use persistence. The backplane holds only control-plane state.

**Packages:** `Altruist`, `Altruist.Redis` · **Docs:** [/docs/deployment/fleet](https://altruist-docs.vercel.app/docs/deployment/fleet), [/docs/deployment/server-node](https://altruist-docs.vercel.app/docs/deployment/server-node), [/docs/deployment/benchmarks](https://altruist-docs.vercel.app/docs/deployment/benchmarks)

Safe by default: the relay signs forwarded client IP headers with HMAC and ignores unsigned ones. The signing key
is `fleet:secret`, and falls back to `altruist:security:key`, so set one of them to a real secret in production.
The drain endpoint answers loopback callers; from outside it needs the `X-Altruist-Drain-Token` header, so set
`drain:token` only if you must call it remotely. The default backplane is in memory; set `fleet:redis` to share it.
Keep your orchestrator's grace period above `drain:timeout + force-grace`.
```yaml
altruist:
  server:
    http: { host: "0.0.0.0", port: 8080 }
    capacity:
      max-load: 200          # 0 = unlimited
    drain:
      timeout: 360           # seconds running work may take
      force-grace: 5
      on-shutdown: true
      token: ""              # optional, for POST /altruist/server/drain from outside loopback
    fleet:
      redis: "redis:6379"    # shared backplane (default: in memory)
      cluster: my-game       # servers with the same name form one fleet
      heartbeat: 2           # seconds
      secret: ""             # relay signature key, default altruist:security:key
```

<a id="game-engine"></a>

## Game Engine and Fixed-Step Loop

The server-side game loop. It runs your [Cycle] methods, timers and effects at a steady frame rate, and steps every registered world once per frame. A fixed-rate stepper gets whole steps of exactly 1/Hz seconds, so a simulation gives the same result however the frames fall. It is created only when the altruist:game:engine section exists.

**Use it when**

- When game logic must run at a steady rate (30 or 120 Hz) whatever the clients do.
- When you want a [Cycle] method, a delayed effect or a cron job on the game loop.
- When you need an authoritative simulation that steps at a fixed rate (for example a 60 Hz match) through IWorldStepper.
- When a socket handler must hand work to the loop (WaitForNextTick, SyncCommit) instead of locking shared state.

**Don't use it when**

- When you only need a periodic background job with no game state, and no game engine is configured. Use a plain hosted service.
- When you need deterministic tick logic that the TypeScript client also runs. Write that logic with [flow] and call it from a stepper.

**Packages:** `Altruist.Gaming` · **Docs:** [/docs/altruist/engine](https://altruist-docs.vercel.app/docs/altruist/engine)

```yaml
altruist:
  game:
    engine:
      framerateHz: 120          # sampling rate of the loop
      world-step: inline        # worker (default) or inline
      fixed-step:
        max-steps-per-frame: 8
        overrun: drop           # drop | carry | slow-motion
```

```csharp

public class MatchSimulation : IWorldStepper
{
    public StepMode Mode => StepMode.Fixed;
    public int FixedHz => 60;

    public void BeforeSteps(in FrameInfo frame) { }
    public void FixedStep(in FixedStep step) => Advance(step.Dt);
    public void AfterSteps(in FrameInfo frame) { }
}

// A method on the game loop, 10 times per second.
[Cycle(10, CycleUnit.Hz)]
public void Housekeeping() { }
```

## Game Worlds and the World Coordinator

A world is a spatial container for game objects. It owns the physics world, the partitions, spawning and spatial queries. This capability holds the dimension-neutral parts: the world index from config, the WorldCoordinator that steps every world once per frame, the world object contracts, and the PlayerEntity base. The 2D and 3D parts are in worlds-2d and worlds-3d.

**Use it when**

- When you declare one or more worlds in config.yml (size, gravity, partition size, optional JSON data file).
- When you spawn and look up world objects through IGameWorldOrganizer and IWorldObject.
- When you want one large world with many maps, each a zone, or several separate worlds.

**Don't use it when**

- When you need a physics world that you own and step yourself, with no organizer, entities or visibility. Use [physics-2d].
- When your game is rooms and matches rather than a persistent spatial world. Use the rooms package.

**Packages:** `Altruist.Gaming` · **Docs:** [/docs/gaming/worlds](https://altruist-docs.vercel.app/docs/gaming/worlds)

```yaml
          size: { x: 1000, y: 1000, z: 1000 }

          data-path: "Resources/world.json"   # optional
```

## 3D Worlds

The 3D implementation of worlds: the 3D organizer and manager, the octree-style partitioner and spatial grid, the world JSON loader, entity synchronization, and the force and trajectory runtimes. Use it when altruist:environment:mode is 3D.

**Use it when**

- When your game is 3D (MMO, action, FPS).
- When you load static geometry, colliders and archetype objects from a world JSON file, or replace the loader with IWorldLoader3D.
- When you spawn objects with full physics (SpawnDynamicObject) or spatial tracking only (SpawnLightweight).

**Don't use it when**

- When your game is 2D. Use [worlds-2d].
- When you only need terrain heights and walkability without physics. Use [terrain].

<a id="navmesh"></a>

## Navigation Mesh and Pathfinding

Builds a navigation mesh from a walkability grid and terrain, finds paths on it (A* plus funnel smoothing), and moves agents along those paths. NavMeshService holds one mesh per zone name. NavMeshRuntime ticks body-bound agents.

**Use it when**

- When NPCs or monsters must walk to a target around obstacles in a 3D world.
- When you need a reachability check, a random point on the mesh, or a line-of-walk test inside a zone.
- When you have a raw navmesh JSON (vertices and indices) to load.

**Don't use it when**

- When movement is grid-based and a walkability check per step is enough. Use [walkability-grid].
- When you need a player-controlled character with slopes and jumping. Use [character-movement].

**Packages:** `Altruist.Gaming`

```csharp
[Service]
public class Patrol(INavMeshService navMesh, INavMeshRuntime runtime)
{
    public void Setup(IWalkabilityGrid grid, ITerrainProvider terrain, IPhysxBody3D body)
    {
        var graph = NavMeshBuilder.Build(grid, terrain);          // null when nothing is walkable
        if (graph != null) navMesh.RegisterMesh("forest_01", graph);

        var agent = runtime.CreateAgent("forest_01", body, speed: 3.5f);
        agent.SetDestination(from: body.Position, to: new Vector3(40, 0, 25));
    }

    // Call once per world step; nothing calls it for you.
    public void Step(float dt) => runtime.Update(dt);
}
```

## Terrain, Heightmaps and Spatial Queries

**Use it when**

- When you load a heightmap image as terrain collision in a physics world.

**Don't use it when**

- When physics is on and you only need ray or capsule casts. Use the physics world API in [physics-3d].
- When you need paths around obstacles. Use [navmesh].

## Zones

Zones are named rectangular regions inside a world (a town, a forest, a dungeon). Each has a position and size and must fit inside one partition. You register them on world.Zones and ask which zone contains a point. Managed zones switch on while players are in them.

**Use it when**

- When one big world holds many maps and you need to know which map a position belongs to.
- When you want zone enter and exit logic, or zone-based entity spawning with IZoneSpawnHandler.

**Don't use it when**

- When you need separate physics worlds for isolated areas. Declare several worlds in [worlds].
- When you need walkable-or-blocked cells inside a zone. Use [walkability-grid].

**Packages:** `Altruist.Gaming` · **Docs:** [/docs/gaming/zones](https://altruist-docs.vercel.app/docs/gaming/zones)

```csharp
var world = _worldOrganizer.GetWorld(0)!;

// Throws ZoneValidationException if the zone is bigger than a partition or straddles two.

    name: "town_01",
    position: new IntVector3(0, 0, 0),
    size: new IntVector3(50000, 50000, 50000)));

var zone = world.Zones.FindZoneAt(32000, 18000, 0);   // IZone3D? or null
```

**Key types**

- `Altruist.Gaming.IZone`: A named spatial region within a world.

## Entity Hibernation

Parks entities that no player can see, so they stop costing tick time, and wakes them when an observer comes near. The framework hibernates zero-observer entities automatically; you decide what hibernating means for your entity.

**Use it when**

- When thousands of NPCs or monsters exist but only the ones near players need to be simulated.
- When your entity must save or clear state when it goes to sleep (IHibernatable.OnHibernate and OnWake).

**Don't use it when**

- When you need to remove an entity for good. Despawn it.

```csharp
    public bool CanHibernate => !InCombat;
    public void OnHibernate() { /* stop timers */ }
    public void OnWake() { /* resume */ }

```

<a id="visibility"></a>

## Visibility (Interest Management)

Decides every tick which observers can see which world objects, diffs that against the last tick, and raises visible and invisible events. It does not send spawn or despawn packets; your game does that in the event handlers. It also feeds entity hibernation and sync broadcasting.

**Use it when**

- When a client should only know about entities near its player.
- When you must send a spawn or despawn packet to a client at the moment an entity enters or leaves its view.
- When you need to know who is looking at an entity (GetObserversOf).

**Don't use it when**

- When you need to broadcast one packet to everyone near a point. Use [spatial-broadcast].
- When the game has no spatial world, such as a lobby or card game. Skip it.

**Packages:** `Altruist.Gaming` · **Docs:** [/docs/gaming/visibility](https://altruist-docs.vercel.app/docs/gaming/visibility)

```yaml
altruist:
  game:
    visibility:
      range: 5000        # world units, the default
```

<a id="spatial-broadcast"></a>

## Spatial Broadcast

Sends a packet only to the clients that can see an entity, using the visibility sets and the spatial hash grid. It saves bandwidth in big worlds, where most clients are far from any one event.

**Use it when**

- When you replicate an entity's state or event to the players who observe it.
- When you need a broadcast limited to nearby partitions instead of the whole room.

**Don't use it when**

- When every connected client must get the message. Use the router's broadcast sender.
- When you replicate an authoritative match room. Send the game's own snapshots through the rooms package.

**Packages:** `Altruist.Gaming` · **Docs:** [/docs/altruist/spatial-broadcast](https://altruist-docs.vercel.app/docs/altruist/spatial-broadcast)

## Lag Compensation

Keeps a short history of entity positions and lets the server rewind the world to the tick a client saw when it acted. Use it to judge hits fairly for players with latency. Live transforms are never changed; the rewind uses an override map.

**Use it when**

- When hit or melee validation must use where targets were on the client's screen, not where they are now.
- When a packet must carry the client's tick (implement ILagCompensated).

**Don't use it when**

- When the client predicts and the server simulates the same fixed-step logic. Use [flow] with prediction instead.
- When gameplay is not spatial or time-sensitive.

**Packages:** `Altruist.Gaming` · **Docs:** [/docs/gaming/lag-compensation](https://altruist-docs.vercel.app/docs/gaming/lag-compensation)

```yaml
altruist:
  game:
    lag-compensation:
      history-ticks: 64          # about 2.5 s at 25 Hz
      snapshot-strategy: nearest # or interpolate
```

```csharp

{
    var (ax, ay, az) = _lagCompensation.Compensate(attacker.VirtualId, attacker.X, attacker.Y, attacker.Z);
    var yaw = _lagCompensation.CompensateYaw(attacker.VirtualId, attacker.FacingYaw);

});
```

## AI Behaviors

Write a monster's brain as a plain class with [AIBehavior] and [AIState] methods. The framework finds the class, makes one state machine per entity, ticks it every engine frame, skips hibernated entities and cleans up when an entity leaves. Also has a receding-horizon planner for bots that plan ahead.

**Use it when**

- When NPCs or monsters need states such as idle, chase, attack and return.
- When bots in a match room need the same behaviors with a machine you create and tick yourself.
- When an agent must plan a short sequence of actions (RecedingPlanner).

**Don't use it when**

- When you need a state machine that is not AI (a door, a combo, a quest). Use [state-machines].
- When bot decisions must replay exactly on a TypeScript client. Use the UtilitySelector in [flow].

**Packages:** `Altruist.Gaming` · **Docs:** [/docs/gaming/ai](https://altruist-docs.vercel.app/docs/gaming/ai)

```csharp
[AIBehavior("aggressive_monster")]
public sealed class AggressiveMonsterBehavior
{

    [AIState("Attack", Delay = 1.5f)]
    public string? Attack(MonsterAIContext ctx, float dt) { DealDamage(ctx); return "Chase"; }

    [AIStateEnter("Chase")]
    public void OnChase(MonsterAIContext ctx) { }
}

[WorldObject("monster")]
public sealed class MonsterEntity : WorldObject3D, IAIBehaviorEntity
{
    public string AIBehaviorName => "aggressive_monster";
    public IAIContext AIContext { get; set; } = null!;
}
```

**Key types**

- `Altruist.Gaming.IAIBehaviorEntity`: Implement on world objects that should be ticked by the AI behavior system.
- `Altruist.Gaming.IAIContext`: AI-specific context marker over the generic state machine core.
- `Altruist.Gaming.AIBehaviorService`

**Services**

- `Altruist.Gaming.AIBehaviorService` as `Altruist.Gaming.IAIBehaviorService` Only when altruist:game is set.

**Attributes**

<a id="state-machines"></a>

## State Machines

A generic finite state machine for gameplay: doors, combos, boss phases, quests, match phases. State methods return the next state name. You build an immutable definition once, make one machine per context, and call Update. It has timing windows and motion curves for combos and attacks. The AI layer is built on it.

**Use it when**

- When something has named states with timed transitions and you want no switch statements.
- When an attack or combo needs timing windows (a hit window, a cancel window) and a motion profile.
- When the machine has no world entity, such as a bot in a match room.

**Don't use it when**

- When you want automatic discovery and per-entity ticking for monsters. Use [ai-behaviors].
- When the same state logic must run bit for bit on a TypeScript client. Use [flow], which adds Advance and RunState.

**Packages:** `Altruist.Gaming`, `@altruist/sim2d` · **Docs:** [/docs/gaming/state-machines](https://altruist-docs.vercel.app/docs/gaming/state-machines), [/docs/gaming/combo-state-machine](https://altruist-docs.vercel.app/docs/gaming/combo-state-machine)

```csharp
[StateBehavior("door")]
public sealed class DoorBehavior
{
    [State("Closed", Initial = true)]
    public string? Closed(DoorContext ctx, float dt) => ctx.OpenRequested ? "Opening" : null;

    [State("Opening")]
    public string? Opening(DoorContext ctx, float dt) => ctx.Progress >= 1f ? "Open" : null;
}

var def = new StateMachineBuilder<DoorContext>()
    .RegisterHandlers<DoorBehavior>()
    .ConfigureState("Opening").Duration(0.75f)
    .Build();

var fsm = new StateMachine<DoorContext>(def);
fsm.Initialize(context);
fsm.Update(context, dt);          // from your own tick
```

**Key types**

- `Altruist.Gaming.StateMachine<TContext>`: Generic FSM driver.
- `Altruist.Gaming.StateMachineBuilder<TContext>`: Composes a `StateMachineDef` from attribute-decorated handler classes, programmatic overrides, or both.
- `Altruist.Gaming.IStateContextCore`: Base context for any state machine consumer.
- `Altruist.Gaming.StateMotionProfile`: First-class Altruist state-machine motion payload.

**Attributes**

- `[State]`: Marks a method as a state update handler.
- `[StateBehavior]`: Marks a class as a source of state-machine handlers.
- `[StateEnter]`: Marks a method as a one-shot hook called once on transition into the named state.
- `[StateExit]`: Marks a method as a one-shot hook called once on transition out of the named state.
- `[StateWindow]`: Attaches a normalized window to a state.

<a id="flow"></a>

## Flow (Deterministic Tick Building Blocks)

Small helpers for the code that runs every tick of a real-time match: ordered rule lists (FirstMatch), tick phases (TickPipeline), modifier stacks, bot utility choice, timers, input edges, entity registries and event sinks. They run in a fixed order with no allocation, and the TypeScript version behaves the same, so server and client compute the same result. It is for deterministic tick logic shared by server and client.

**Use it when**

- When the client predicts the server by running the same simulation, and the two must not drift apart.
- When matches are replayed or rolled back and must give the same result.
- When game modes or tests must insert, replace or remove one rule by name instead of copying a whole Step().
- When bots must make the same choices for the same seed (UtilitySelector with DeterministicRandom).

**Don't use it when**

- When the server only stores state and checks requests (turn-based, lobbies, simple RPG commands). Plain code is fine.
- When you need a state machine for match phases. Use [state-machines].

**Packages:** `Altruist.Gaming`, `Altruist.Physx`, `@altruist/sim2d` · **Docs:** [/docs/gaming/flow](https://altruist-docs.vercel.app/docs/gaming/flow), [/docs/gaming/physics/typescript-sim2d](https://altruist-docs.vercel.app/docs/gaming/physics/typescript-sim2d)

```csharp
using Altruist.Gaming.Flow;

var rules = FirstMatch<HitContext, float>.Create()
    .When("super",   c => c.SuperStrike,   c => cfg.SuperStrikeMultiplier)
    .When("kick",    c => c.Kick,          c => MathF.Max(c.ZoneMult, cfg.Nose) * cfg.FlipKick)
    .Otherwise(c => c.ZoneMult);

// A game mode adds a rule by name, before another one.
rules.Before("super").When("overcharged", c => c.Overcharged, 4f);

var multiplier = rules.Build();            // once, at setup
float mult = multiplier.Evaluate(ctx);     // every tick, no allocation

Countdown.Tick(ref car.DashCooldown, dt);  // t = max(0, t - dt)
```

```ts
// Same shape on the client.
import { FirstMatch } from '@altruist/sim2d/flow';
const rules = FirstMatch.create<HitContext, number>().when('super', c => c.superStrike, () => cfg.superStrikeMultiplier);
```

**Key types**

- `Altruist.Gaming.Flow.FirstMatch<TCtx, TResult>`: Ordered rule selector: the replacement for an `if / else if` ladder that picks a result.
- `Altruist.Gaming.Flow.TickPipeline<TCtx>`: The ordered, named phases of one simulation tick: the replacement for a long `Step()` method whose order is only visible by reading it.
- `Altruist.Gaming.Flow.ModifierStack<TCtx>`: An ordered list of float modifiers (Set / Add / Mul / Min / Max / Map), each optionally conditional, applied in order to a value: the replacement for a block of `if (a) scale = x; else if (b) scale = y; if (c) scale = MathF.Min(scale, z); if (d) scale *= w;`.
- `Altruist.Gaming.Flow.UtilitySelector<TOption, TCtx>`: Utility-based choice between a fixed set of options (roles, tactics, targets): the replacement for a hand-written "score every role, add noise and hysteresis, take the best, then apply the exceptions" block.
- `Altruist.Gaming.Flow.Countdown`: Float timers kept in plain fields (cooldowns, windows, grace times): the named form of `t = MathF.Max(0, t - dt)` and its "just ran out" edge.
- `Altruist.Gaming.Flow.TimerSet`: An indexed set of countdown timers (pad cooldowns, per-slot respawns).
- `Altruist.Gaming.Flow.EntityRegistry<TKey, T>`: The entities of a simulation, always iterated in ascending id order (the deterministic order every per-entity loop needs), with O(1) lookup by id and O(log n) position of an id.
- `Altruist.Gaming.Flow.EventSink<TEvent>`: Collects events in emission order.

## Numerics (Deterministic Math)

The math a simulation keeps rewriting: scalar clamps and approaches, angle wrapping, safe vector normalization, tuning curves, a seeded random generator, positions, rotations and transforms for 2D and 3D, box and ray tests. Each helper evaluates exactly the formula in its summary, so results match bit for bit across runs. The TypeScript package mirrors it.

**Use it when**

- When a simulation must replay exactly or match a client (use DeterministicRandom, not System.Random).
- When you need angle wrapping, Approach, Lerp, PiecewiseLinear curves or safe NormalizeOrZero.
- When you need Position3D, Rotation3D, Transform3D and their 2D twins.

**Don't use it when**

- When you need operations on bodies and contacts. Use [motion-2d] or [physics-2d].
- When exact repeatability does not matter and System.Numerics is enough.

```csharp

```

## Character Controllers and Movement

A server-authoritative kinematic character controller. The client sends input, the controller moves the capsule each tick with gravity, ground probing, slope limits and wall sliding. Movement profiles (FPS, TPS, MMO) and abilities such as jump plug in. There is also a 2D controller, and a simpler input and output movement helper in Physx.

**Use it when**

- When players move in a 3D world and the server must compute the real position.
- When you need walk, sprint, jump or click-to-move with different feels (profiles).

## Combat

A small combat core: one attacker hits one target, or sweeps an area (sphere, cone, line) in 2D or 3D. A damage calculator you replace turns attacker and target into damage, and hit, death and sweep events tell your game what happened. Your game keeps the formulas, rewards and packets.

**Use it when**

- When entities in your world hit each other and you want health, kill and event handling done for you.
- When you need area attacks (cones, spheres, lines) with a target cap and a filter.
- When clients send attack and target packets and you want the built-in portal gates for them.
- When attacks must be checked against where targets were on the attacker's screen (it uses lag compensation when the packet carries a client tick).

**Don't use it when**

- When you need knockback, impulses or projectiles that move bodies. Use the physics and body APIs of the gaming package; this only moves health numbers.
- When your fights are turn-based inside a match room. Put the rules in your room simulation (see rooms) and skip this service.

## Questing

A quest runtime. Quests are classes with attributes for id, name and requirements, and state methods that react to events such as kill, NPC talk, item pickup or timer. The runtime checks requirements, runs your hooks, saves progress and tells your game what changed. Your game owns the packets and the UI.

**Use it when**

- When your game has quests with steps, counters and requirements (level, class, faction).
- When quest progress must survive relogs and level changes (reconcile and suspend, without deleting progress).
- When you want quests as plain C# classes found by scanning an assembly.

**Don't use it when**

- When you only need a generic state machine for AI or entities. Use the state machine feature of the gaming package; quests add persistence, requirements and update publishing on top.
- When you want a ready-made quest UI or quest packets. The package sends nothing to clients; you map QuestUpdate to your own packet.

**Packages:** `Altruist.Gaming.Questing` · **Docs:** [/docs/gaming/quest-system](https://altruist-docs.vercel.app/docs/gaming/quest-system)

```csharp
// A quest is a class. The runtime finds it by scanning the assembly.
[Quest("side.gather_ores")]
[QuestName("Gather Ores")]
[QuestRequirement("level", QuestOperator.GreaterOrEqual, 10)]
public sealed class GatherOresQuest : QuestBehavior<GameQuestContext>
{
    [QuestState("talk_to_blacksmith", Initial = true)]
    public string? TalkToBlacksmith(GameQuestContext ctx)
        => ctx.Trigger == QuestTrigger.Npc && ctx.TargetId == BlacksmithNpcId ? "collect_ore" : null;

    [QuestStateEnter("collect_ore")]
    public void EnterCollectOre(GameQuestContext ctx)
    {
        ctx.State.Set("target", 10);
        ctx.State.Set("count", 0);
    }

    [QuestState("collect_ore")]
    public string? CollectOre(GameQuestContext ctx)
    {
        if (ctx.Trigger == QuestTrigger.Item && ctx.TargetId == IronOreItemId
            && ctx.State.Increment("count") >= ctx.State.Get("target", 10))
            return "completed";
        return null;
    }
}

// Host side: you supply the store, the sink (QuestUpdate -> your packet) and requirement evaluators.
var runtime = new QuestRuntime<GameQuestContext>(stateStore, updateSink, requirements, contextFactory);
runtime.LoadFromAssembly(typeof(GatherOresQuest).Assembly);
await runtime.FireAsync(baseContext, QuestTrigger.Item, targetId: IronOreItemId);
```

## Match Rooms

A host for short-lived, authoritative match rooms: a fixed group of players in an isolated instance with its own fixed-step simulation. It handles connections, seats for players and bots, ordered input, snapshots, reconnect, bot refill and room disposal. You write the simulation and the packets. Rooms are a library type, not a [Service]: you build a RoomHost yourself and expose it to the engine.

**Use it when**

- When your game is session-based (matches, rounds, races, arenas) and each match is its own deterministic simulation.
- When you need reconnect grace, bots filling empty seats, team forfeits and clean room disposal.
- When clients predict their own input and the server must apply exactly the client's input stream (see typescript-client).

**Don't use it when**

- When players share one persistent open world. Use the world organizers (2D or 3D) of the gaming package instead.
- When you only need to group players and then start a room. Rooms alone do not queue anyone; add matchmaking (public queues) or lobbies (private invite codes).

**Packages:** `Altruist.Gaming.Rooms` · **Docs:** [/docs/gaming/rooms](https://altruist-docs.vercel.app/docs/gaming/rooms)

```csharp
    public void FixedStep(in FixedStep s) => _host.FixedStep(s);
    public void AfterSteps(in FrameInfo f) => _host.AfterSteps(f);
}
```

## Matchmaking

Public queues for match rooms. Waiting players are grouped by playlist (and rating), bots fill unrated rooms, and queued players can join running rooms (join in progress). It is a module you add to a RoomHost, not a [Service]; there is no config key and the options are passed in code.

**Use it when**

- When strangers queue for a mode (duel, 2v2, ranked) and you want them put into rooms automatically.
- When you want rating windows, bot backfill or join in progress to replace leavers.
- When you run a fleet and want players of one playlist to gather on one server.

**Don't use it when**

- When friends play together through an invite code and a leader picks the mode. Use lobbies instead.
- When you have no match rooms. Matchmaking needs a RoomHost; see rooms.
- When you only need the queue logic in a tool or a test without a host. Use Matchmaker alone.

**Packages:** `Altruist.Gaming.Matchmaking` · **Docs:** [/docs/gaming/matchmaking](https://altruist-docs.vercel.app/docs/gaming/matchmaking), [/docs/client-sdk/matchmaking](https://altruist-docs.vercel.app/docs/client-sdk/matchmaking)

```csharp
// How you turn it on: create the module and add it to your RoomHost. Your game class
// implements IMatchmakingGame<ArenaSim, PadInput, Profile> next to IRoomGame.
var playlists = new[]
{
    new PlaylistOptions { Id = "duel", Mode = "1v1", TeamSize = 1, Rules = new RoomRules { JoinInProgress = true } },
    new PlaylistOptions { Id = "ranked", Mode = "2v2", TeamSize = 2, Rated = true },
};
var mm = new MatchmakingModule<ArenaSim, PadInput, Profile>(game, new MatchmakingOptions { FillAfterSeconds = 10 }, playlists);

// On the engine thread, when a client asks to queue or cancels:

mm.Cancel(session);
```

**Key types**

- `Altruist.Gaming.Matchmaking.MatchmakingModule<TSim, TInput, TPlayer>`: Queues, groups and join in progress on top of the `RoomHost`: waiting players first fill open (or bot) seats of running rooms that allow it — open seats at once, bot seats one at a time with a notice — and otherwise start new rooms; rated playlists group by rating window (and join rated rooms whose mean rating is inside the player's window).
- `Altruist.Gaming.Matchmaking.IMatchmakingGame<TSim, TInput, TPlayer>`: What matchmaking needs from the game; implement it (usually on the same class as `IRoomGame`) when the host uses `MatchmakingModule`.
- `Altruist.Gaming.Matchmaking.MatchmakingOptions`: Timings and windows of matchmaking (passed by the game; not read from configuration).
- `Altruist.Gaming.Matchmaking.PlaylistOptions`: A queue players can join: which room mode it starts, teams and their size, rated or not, and the `RoomRules` of its rooms.
- `Altruist.Gaming.Matchmaking.Matchmaker`: Queues per playlist and the rules that turn waiting players into groups.
- `Altruist.Gaming.Matchmaking.QueueStatusInfo`: A connection's queue status (the game turns it into its packet).

## Lobbies

Private lobbies for match rooms. A player creates a lobby, friends join by invite code, the host picks a mode and starts a room, and everyone comes back to the lobby afterwards. It is a module you add to a RoomHost, not a [Service]; options are passed in code, not read from config.

**Use it when**

- When friends or invited players play together (custom games, training) and a leader starts the match.
- When a group must stay together between rooms and survive a reconnect during a room.

**Don't use it when**

- When strangers should be grouped automatically by playlist or rating. Use matchmaking instead.
- When you have no match rooms. Lobbies start rooms on a RoomHost; see rooms.

**Packages:** `Altruist.Gaming.Lobbies` · **Docs:** [/docs/gaming/lobbies](https://altruist-docs.vercel.app/docs/gaming/lobbies)

```csharp
// How you turn it on: create the module and add it to your RoomHost. Your game class
// implements ILobbyGame<ArenaSim, PadInput, Profile> next to IRoomGame.
var lobbies = new LobbyModule<ArenaSim, PadInput, Profile>(game,
    new LobbyOptions { MaxMembers = 6, Playlist = "private", Rules = new RoomRules { BotRefill = false } });
host.Use(lobbies);

// On the engine thread, on client commands:
lobbies.Join(session, "");          // create a lobby; the code comes back in ILobbyGame.LobbyState
lobbies.Join(session, "K7QXD");     // join by code
lobbies.Start(session, "2v2");      // host only; ILobbyGame.TeamSizeOf("2v2") must not be null
```

**Key types**

- `Altruist.Gaming.Lobbies.LobbyModule<TSim, TInput, TPlayer>`: Private lobbies on top of the `RoomHost`: create or join by code, host migration, start a room with the members (bots fill the teams), return after the room, rejoin a lobby room after a reconnect.
- `Altruist.Gaming.Lobbies.ILobbyGame<TSim, TInput, TPlayer>`: What lobbies need from the game; implement it (usually on the same class as `IRoomGame`) when the host uses `LobbyModule`.
- `Altruist.Gaming.Lobbies.LobbyOptions`: Settings of `LobbyModule` (passed by the game; not read from configuration).
- `Altruist.Gaming.Lobbies.Lobby<TSim, TInput, TPlayer>`: A private group joined by invite code.
- `Altruist.Gaming.Lobbies.LobbyMember<TPlayer>`: One member of a `Lobby`.

## Live Dashboard

The operations and debugging UI of a running server, served at /altruist/dashboard with JSON APIs under /dashboard/v1. It shows config, engine, fleet, connections, worlds, rooms, caches, vaults and traffic, and it can act: edit live config, drain the server, close rooms, run SQL, call any endpoint. A VS Code extension opens the same app in an editor tab. It is off until you turn it on, and it is an admin surface that must be protected.

**Use it when**

- When you develop or run a server and want to see the engine, worlds, rooms, traffic and fleet live.
- When you want to draw debug shapes (spawn areas, aggro radii, paths) over a world with the gizmo registry.

**Don't use it when**

- When you need metrics and alerts for production monitoring. Export telemetry to a monitoring tool; the dashboard is an admin tool, not a monitoring system.
- When the server is public and you have not set a token or a policy. Outside Development every dashboard request is refused with 503 until you do.

**Packages:** `Altruist.Dashboard`, `altruist-dashboard-vscode` · **Docs:** [/docs/gaming/dashboard](https://altruist-docs.vercel.app/docs/gaming/dashboard), [/docs/gaming/dashboard/vscode-extension](https://altruist-docs.vercel.app/docs/gaming/dashboard/vscode-extension)

Reference the Altruist.Dashboard package, then turn it on and protect it. Security:
- `token` is a shared secret of at least 16 characters (shorter counts as not set). Whoever has it can run SQL on your vaults, edit config, disconnect players and drain the server. Keep it in an environment variable.
- `policy` names an ASP.NET Core authorization policy you register; signed-in users who satisfy it get in. If both are set, either grants access.
- With neither set, in Development only, loopback requests (same machine) get in without credentials. `allow-loopback-without-token: false` turns that off. Requests that carry proxy headers are never treated as loopback.
- With neither set outside Development, the server still runs but every dashboard request answers 503. Nothing is exposed.
- Do not put the dashboard on the public internet without a strong token or policy and TLS. The browser login is `?dashboard_token=...` once, then an HttpOnly cookie.

```yaml
altruist:
  dashboard:
    enabled: true
    token: ${DASHBOARD_TOKEN}      # >= 16 characters; or: policy: ops
    allow-loopback-without-token: true   # Development only; default true
    network:                       # traffic recorder (on by default when the dashboard is on)
      enabled: true
      maxEvents: 10000
      maxPayloadBytes: 32768
      redactFields: [password, token, authorization]
    world:
      renderScale: 1
      terrainSampleStride: 1       # raise for large heightfields
```

## .NET Client

A client library for talking to an Altruist server from .NET: Unity, Godot, Blazor, console tools and test harnesses. It speaks the server's wire protocol over TCP, UDP or WebSocket with a MessagePack or JSON codec, and dispatches incoming packets to methods marked [Packet]. Transports are chosen in config.

**Use it when**

- When a .NET program (Unity, Godot, a bot, a load test) must connect to an Altruist server.
- When you want one router that sends by gate name and can pick TCP, UDP or WebSocket per message.
- When incoming packets should be routed by message code to your handler methods.

**Don't use it when**

- When the client is a browser game. Use the typescript-client packages instead.
- When you write end-to-end tests of your own server in the same repo. Use the testing capability (Altruist.Testing); it has test clients with the same shape.

**Packages:** `Altruist.Client` · **Docs:** [/docs/networking/client-packets](https://altruist-docs.vercel.app/docs/networking/client-packets)


## TypeScript Client SDK

Dependency-free TypeScript packages for browser game clients. @altruist/net has the MessagePack wire format, the WebSocket transport (tickets, reconnect, heartbeat, fleet redirect) and ping and clock diagnostics. @altruist/client adds HTTP auth, the matchmaking and lobby flow, and device pairing. @altruist/input and @altruist/prediction match the server's room input and fixed-step clock, so the client can predict its own player exactly.

**Use it when**

- When a browser game connects to an Altruist server and you want the socket, token refresh and packet routing done.
- When the game queues or joins lobbies and you want the phase machine that mirrors MatchmakingModule and LobbyModule.
- When the client predicts its own movement against a RoomHost and must send inputs in the order and rate the server's input buffer expects.

**Don't use it when**

- When the client is .NET (Unity, Godot, console). Use the dotnet-client package.
- When you only need the 2D physics and gameplay helpers to run the same simulation in the browser. That is typescript-sim2d.

**Use it when**

- When the browser must reproduce server physics or gameplay exactly (client-side prediction, replays).

- When you only need sockets, auth or matchmaking in the browser. Use typescript-client.
